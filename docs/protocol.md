# copywhere 协议与设计说明

本文描述 copywhere 的节点发现机制与传输协议，供二次开发与排障参考。

## 1. 节点身份

### 1.1 稳定指纹（ID）

节点 ID = `sha256("guid:" + MachineGuid)[:16]`（十六进制）。

- 来源：Windows 注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`，
  系统安装时生成，重装系统才会变化。
- 读取失败时退回 `sha256("host:" + 主机名 + "|" + 全部网卡MAC)[:16]`。
- 特性：同一台机器**重启进程、重启系统后 ID 均不变**，对端据此把它的全部
  来源地址合并到同一节点，不会误判为新节点。

### 1.2 会话（Session）

每次 `copywhere` 进程启动生成 8 字节随机会话标识，随公告广播。
**同一 ID 的会话变化 = 该节点进程重启**。发送方借此解除因鉴权被拒
（未配对/配对已被对端解除）对节点施加的"暂停发送"状态并重新尝试；
若仍未配对会再次被拒并重新暂停。

## 2. 节点发现（UDP）

- 端口：`discovery_port`（默认 47830/udp）。
- 公告周期：`announce_interval_sec`（默认 2s），启动即发一次。
- 发送目标：本机每个 IPv4 网段的**定向广播地址**（如 `192.168.0.255`）
  以及 `127.0.0.1`（便于同机联调）。

公告为单行 JSON：

```json
{
  "magic":   "copywhere-a1",
  "id":      "节点指纹（16位hex）",
  "name":    "节点显示名",
  "tcp_port": 47831,
  "session": "随机会话标识（16位hex）",
  "caps":    ["rich"]
}
```

接收方：监听 `0.0.0.0:discovery_port`，校验 `magic`，过滤自身 ID，
以 ID 为键维护节点表。

`caps` 是公告方支持的**能力清单**（能力协商，天然向后兼容）：旧版本不认识
该字段（JSON 忽略未知键）解析后为空，新版本据此决定是否使用扩展消息类型。
当前已定义的能力：

| 能力 | 含义 |
|------|------|
| `rich` | 接受 `type="rich"` 的带格式文本（HTML/RTF）同步 |

同一指纹的节点会话变化（进程重启，可能已降级版本）时，已记录的能力作废，
以新公告为准。

### 2.1 节点表与地址策略

- 存活判定：超过 `peer_ttl_sec`（默认 12s）未收到公告即离线；重新收到公告即上线。
- **地址全保留**：同一节点从多个网络（局域网、ZeroTier 等）广播来的每个
  来源 IP 都记录（去重按 IP 本身），节点只显示一份。
- 优选排序按评分降序（同分按最近活跃倒序）：`192.168.*` 计 3（真实局域网，
  恒优先于虚拟/中继网段）；与本机同网段的直连地址计 2；其余计 0。
- 发送方**依次尝试每个地址，任一成功即成功**——优选路径失效不会失联。
- 地址剔除：某地址超过 5 分钟无公告则从候选中移除。

## 3. 传输协议（TCP）

- 端口：`transfer_port`（默认 47831/tcp）。
- 报文结构：`单行 JSON 头(\n) + 原始负载 + 单行 JSON 应答(\n)`。

### 3.1 请求头

```json
{
  "v":         1,
  "token":     "鉴权令牌（共享 token 或本节点签发给发送方的配对令牌）",
  "type":      "file | text | rich | pair | kvm",
  "name":      "文件名（text 时为 text，rich 时为 rich）",
  "size":      12345,
  "sha256":    "负载摘要",
  "sender":    "发送方节点显示名",
  "sender_id": "发送方节点指纹（配对令牌校验依赖；可省略）",
  "bundle":    true
}
```

`bundle=true` 仅当负载是发送端因多文件/目录而**临时打包的合成 zip**时出现——
接收端据此自动解包；用户亲手发送的单个 zip 文件不带该标记，原样落盘不解包。

限制：单文件 ≤ 4GB，文本 ≤ 4MB，rich 负载 ≤ 16MB，pair / kvm 负载 ≤ 64KB。token 使用常数时间比较校验。

**鉴权规则**（接收端，仅认配对令牌）：

`sender_id` 必须在本机配对列表（peers.json）中，且 `token` == 本机签发给该节点的配对令牌（常数时间比较）。未配对节点一律拒绝。

### 3.2 配对（type = pair）

配对用于交换**逐对独立**的令牌（存于 `~/.copywhere/peers.json`，与 config token 分离）：

```
A（发起方）                              B（被请求方）
  │ Header{type:"pair"} + 负载             │
  │ {id:A_ID, name:A名, token:t_AB}  ────▶ │ 弹出「接受配对」确认（人工裁决，
  │                                        │ 连接保持打开，150s 内有效）
  │                                        │ 接受：签发 t_BA 并入库
  │ ◀──── Response{ok:true, token:t_BA,   │ （应答沿原连接返回，不可伪造）
  │              peer_id:B_ID, ...}        │
  │ 入库 entry{B: pair=t_AB, peer=t_BA}    │ 入库 entry{A: pair=t_BA, peer=t_AB}
```

- 此后 A→B 携带 `t_BA`，B→A 携带 `t_AB`；任一方解除配对即删除记录，立即双向失效。
- 拒绝时应答 `{ok:false, error:"pair rejected"}`。
- 配对是唯一的准入方式：未配对节点的任何传输请求都会被拒绝。

### 3.3 应答

```json
{ "ok": true,  "path": "接收后的最终路径", "duplicate": false }
{ "ok": false, "error": "unauthorized | sha256 mismatch | ..." }
{ "ok": true,  "token": "对端签发的配对令牌", "peer_id": "对端指纹", "peer_name": "对端名" }
```

`duplicate=true` 表示对端子目录内已存在相同内容（同路径同 sha256），不重复落盘
（每次接收独占新建子目录，正常传输不会触发）。

### 3.4 接收流程

1. 在接收目录下为本次传输创建**独立子目录** `<20060102-150405>-<发送方名>`
   （同秒冲突追加 `-2`、`-3`……`os.Mkdir` 排他创建保证并发安全）；
2. 落盘为子目录内 `.cw-partial-*` 临时文件，边接收边计算 sha256；
3. 校验 size 与 sha256，失败即删除临时文件与空子目录并回错误应答；
4. 文件以**原始文件名**原子改名到子目录内，不做重命名；
5. 若头部带 `bundle=true` 且为 zip：应用层解包到同一子目录并删除 zip 本体，
   剪贴板回贴解包结果（顶层目录或全部顶层条目）；解包失败保留原 zip；
6. 应答；随后按 `auto_paste` / `text_sync` 配置写入本机剪贴板。

### 3.5 KVM 布局同步（type = kvm）

负载 `{"peer_id":"发送方指纹","peer_name":"发送方名","side":"left|right","clear":true?}`：

- `clear` 缺省（false）：语义为"把我放到你的 side 侧"。接收端（已通过配对
  令牌鉴权）把对方登记到 kvm_left/right、落盘并热更新本机 KVM 服务；
- `clear: true`：语义为"把我从你的 side 侧移除"。接收端仅当该侧当前确实
  是发送方时才清空并落盘生效（迟到的取消消息不会覆盖本机较新的布局）。

两种消息接收后均应答 `{ok:true}`。面板保存布局时触发：设置与取消
（含把某侧邻居换成其他节点时向旧邻居推送取消）都会同步到对端，
实现多机自动同步。

> **兼容性**：v0.2 及更早版本不认识 `clear` 字段（JSON 反序列化忽略未知
> 字段），会把取消消息**误解为普通"设置"**并写入错误布局。混合版本运行
> 期间取消/换人同步不可用且有害——`kvm` 协议变更要求**所有节点同步升级**
> 到 v0.3+ 后取消同步才可用（升级步骤见 release.md）。

### 3.6 带格式文本（type = rich）

借鉴 MouseWithoutBorders 的富文本同步（其只搬运 RTF），copywhere 把
`CF_UNICODETEXT`、`HTML Format`、`Rich Text Format` 三种格式一并搬运，
负载为单行 JSON：

```json
{ "text": "纯文本兜底（必填）", "html": "VmVyc2lvbjogMS4w…", "rtf": "e3xydGYx…" }
```

（`html`/`rtf` 为对应剪贴板格式的**原始字节**，含各自编码的 BOM，不做转码；
Go 的 `[]byte` 经 JSON 上线为 **base64 字符串**——非 Go 实现方按 base64
解码即可还原原始字节。CF_HTML 的 `StartFragment`/`EndFragment` 偏移指向
块内自身，跨机整体复制后仍然有效。）

- **能力协商**：发送端只对公告了 `caps:["rich"]` 的节点使用本类型；对旧版本
  节点自动降级为 `type="text"` 携带纯文本。混合版本环境一次复制全覆盖，
  旧版本永远不会收到无法处理的消息，无需协议版本号。
- 限制：rich 负载（JSON 序列化后）≤ 16MB，超出只保留纯文本走 text 通道。
- **魔数轻校验**（两端一致）：HTML 须以 `Version:` 开头（CF_HTML 规范），
  RTF 须以 `{\rtf` 或 `{\*\rtf` 开头，不符则丢弃该格式仅保留纯文本——
  不把畸形内容递给本机应用的 HTML/RTF 解析器（Word/浏览器粘贴时会解析
  这些格式）。
- 接收端写回剪贴板时一次 `EmptyClipboard` + 逐格式 `SetClipboardData`，
  使目标应用粘贴时自行挑选最丰富的格式（Word 保留样式、浏览器保留排版）。

### 3.7 超时预算

- 接收端：`60s + size / 256KB/s`（对 ZeroTier 中继等慢链路宽裕）。
- 发送端：文件在上述基础上再 +30s，文本 +15s，保证发送端不会先于接收端超时。
- 发送端严格按头部声明的 `size` 发送（`io.CopyN`）：文件中途变化宁可报错，
  也不多发字节，避免接收端带着未读数据关连接（RST）导致应答丢失。

## 4. 剪贴板同步与防回环

- **事件驱动 + 轮询兜底**：主通道用 `AddClipboardFormatListener` 注册消息专用
  窗口，剪贴板一变即收 `WM_CLIPBOARDUPDATE`（毫秒级）；同时保留 400ms 轮询
  `GetClipboardSequenceNumber` 作降级兜底（监听安装失败时回退旧式
  `SetClipboardViewer` 链，再不行只剩轮询）。两条路径汇入同一个容量 1 的
  合并事件通道，唤醒检测循环；面板 `api/status` 的 `watch_mode` 字段与
  `/api/debug` 快照可查证当前生效的监听方式。
- 变化即按 **文件 → 文本 → 截图** 的优先级读取：CF_HDROP（文件）、
  CF_UNICODETEXT + HTML Format + Rich Text Format（文本）、图片（截图）。
- 文本读取走富格式版本（见 3.6）：只有纯文本时与旧行为完全一致；带
  HTML/RTF 时一并通过 rich 通道搬运（对旧版本自动降级为纯文本）。
- 带文本的位图（Excel/Word 等复制时附带的预览位图）按文本处理，不会误当截图发送。
- 截图同步：无文件无文本时读取图片——优先取应用直接放入的 "PNG" 注册格式
  （Win+Shift+S 等截图工具常提供），否则将 CF_DIB 位图就地转换为 PNG
  （支持 24/32bpp 的 BI_RGB / BI_BITFIELDS）。PNG 字节落盘到接收目录的
  「截图」子目录（`截图_<时间戳>.png`）后按普通文件通道发送与重试；
  同一张截图（内容 sha256 前 8 字节指纹）不重复发送，受 `max_auto_copy_mb`
  阈值约束。
- 防回环双重防护：
  1. 本进程写剪贴板后记录新的序号（OwnSeq），事件与轮询都跳过；
  2. 收到远端内容后 3 秒冷却期内忽略剪贴板变化（兜底竞态窗口）。
     接收端写回富文本时只清空一次剪贴板、逐格式 `SetClipboardData`，
     避免"先写文本再写 HTML"的中间状态被自己的监听捕形成回环。
- 阈值：文件总大小（目录递归统计）超过 `max_auto_copy_mb` 不自动同步，
  仅记日志，可用 `send` 命令或在 gui 面板手动发送（拖入文件 / 文本框，不受阈值限制）。
- 暂停开关：面板或托盘可暂停自动同步（Paused 标志），暂停期间剪贴板变化被
  跳过（内容不累积），恢复后不补发。

## 5. 运行时诊断（面板端点，非节点间协议）

仅绑定 `127.0.0.1`、复用面板访问令牌鉴权，供排障使用：

| 端点 | 说明 |
| --- | --- |
| `GET /api/debug` | JSON 快照：事件计数（clip.events / recv.files / send.conns / kvm.* / discovery.*）、各主循环心跳年龄、会话状态（KVM 主从、剪贴板监听方式）、协程数/堆内存、环形日志尾部。`Accept: text/html` 时返回自动刷看的诊断页 |
| `POST /api/debug/stack` | 转储全部协程栈到环形日志（含 watchdog 卡死时的自动转储），返回转储块数 |

主循环（announce / monitor / flush）每轮打点心跳，watchdog 以各自预算判定
卡死并自动转储一次（恢复前不重复）。诊断只读快照与轻量打点，不在热路径加锁。

## 6. 多文件打包与自动解包

- 多个对象或目录自动打包为 `copywhere-bundle-<时间戳>.zip`（Deflate），
  zip 内部保留相对目录结构，重名自动追加 `(n)`；发送时头部带 `bundle=true`。
- 接收端把该 zip 解包到本次接收子目录并删除 zip 本体，剪贴板回贴解包结果：
  单个顶层目录（文件夹传输）或全部顶层条目（多文件传输），Ctrl+V 粘贴的
  与发送端复制的内容一致。
- 用户亲手发送的单个 zip 文件不带 `bundle` 标记，接收后**原样保留**，
  剪贴板回贴 zip 本身——不会被误解包。
- 旧版本对端不识别 `bundle` 字段，会把合成 zip 当普通文件保存，行为向后兼容。

## 7. 容错行为

| 场景 | 行为 |
| --- | --- |
| 对端拒绝（未配对/token 不一致） | 提示一次后**暂停向该节点发送**，不重试；完成配对或对端修正后自动恢复 |
| 对端短暂离线 | 内容暂存 60s，期间周期性对在线节点重试 |
| 优选地址失效 | 自动尝试该节点其余已知地址 |
| 链路过慢 | 按预算超时，接收端日志记录不完整的具体字节数 |

## 8. 鼠标键盘跨屏（KVM）

软 KVM：主控机捕获本地输入流式转发，副机注入。不传画面，只传事件。

- 端口：`kvm_port`（默认 47832/tcp），报文为单行 JSON（`\n` 分隔）。
- 鉴权与能力协商：首条消息 `{"t":"hello","token":...,"id":"主控机指纹","name":...,"abs":true,"mw":2880,"mh":1800,"mscale":2.0}`，
  对端回 `{"t":"ok","pw":1920,"ph":1080,"pscale":1.0,"abs":false}` 或 `{"t":"error","msg":"unauthorized|busy"}`。
  - `mw/mh/mscale` 与 `pw/ph/pscale`：两端当前/入口显示器的物理分辨率与实际设置缩放比（通过 Windows `GetDpiForMonitor` 读取），用于相对通道静态计算科学基准增益；
  - `abs`：Universal 坐标通道能力位。仅在双方均声明支持且**被控端为单显示器**时启用；若被控端拥有多台显示器，自动协商退回相对位移通道，以确保光标能自然漫游跨入副屏。
  - 令牌校验：主控机携带被控机签发给它的配对令牌，被控机按 `id` 查本机签发的配对令牌比对；任一方未配对即拒绝。
- 布局同步：两端通过传输通道的 `kvm` 类型互推"把我放到你的 X 侧"，
  接收端更新 kvm_left/right 并热生效（与配对一样只允许已配对节点）。

### 8.1 消息

| 方向 | 消息 | 说明 |
| --- | --- | --- |
| 主→副 | `{"t":"enter","dir":"right|left","y":0.42}` | 接管副机；dir 是光标离开主控屏的方向，y 是主控机光标在主控离场屏内的高度比例 |
| 主→副 | `{"t":"move","dx":12,"dy":-3}` | 相对通道：自上次发送以来的累计位移（叠加跨分辨率/缩放比静态增益与亚像素结转）。多屏被控端或未协商 `abs` 时发送 |
| 主→副 | `{"t":"umove","ax":34133,"ay":8192}` | Universal 通道：光标在被控单屏上的绝对归一化坐标（0..65535）。仅协商 `abs: true` 时发送 |
| 主→副 | `{"t":"btn","b":1..5,"down":bool}` | 鼠标按键 |
| 主→副 | `{"t":"wheel","d":-120,"h":false}` | 滚轮 |
| 主→副 | `{"t":"key","vk":65,"scan":..,"down":bool,"ext":bool}` | 键盘 |
| 主→副 | `{"t":"ping"}` | 1s 保活 |
| 副→主 | `{"t":"pong"}` | 对 ping 的应答（刷新主控端读超时） |
| 副→主 | `{"t":"leave"}` | 光标推回共享边缘 / 看门狗超时，交还控制权 |

> 未识别的 `t` 一律忽略。

### 8.2 多显示器、切换与切回

- **暴露边缘**：某显示器某侧没有相邻的本地显示器（坐标容差 2px、垂直方向有重叠）才算暴露。只有暴露边缘能触发切换——双屏之间光标会自然滑过去的内侧边界不触发。
- **切入**：光标推向暴露边缘并继续推动（Raw Input 贴边位移累计 ≥8px，轻推即过）→ 连接邻居，副机把光标放到入口显示器的共享边缘；入口高度按主控比例映射。
  退化显示器矩形（虚拟/幽灵显示器适配器枚举出的 1x1 占位项，<100px）不参与入口选择。
- **被控移动**：
  - **相对通道（多屏被控推荐）**：静态跨分辨率与实际设置缩放比补偿。主控端根据两端分辨率与缩放比折算逻辑视口计算固定增益（$gain = \frac{W_s \times Scale_m}{W_m}$），再结合亚像素余数结转与面板微调百分比（`kvm_speed_percent`），绝不随手速漂移，光标可在被控端所有显示器间自由漫游；
  - **Universal 通道（单屏副机适用）**：映射为 0..65535 屏幕绝对归一化坐标，副机通过 `SetCursorPos` 进行绝对定位注入，绕开副机的指针速度/加速曲线。
- **移动合拍（主控端）**：原始移动按 `kvm_move_interval_ms`（默认 8ms，≈125Hz）合拍后发送，兼顾流畅与带宽。
- **重排注入（被控端）**：合拍事件经 TCP 成批到达后，若逐包直注会出现微小台阶感。默认（`kvm_reflow_step_ms=4`，≈250Hz）由独立协程按固定节拍排空待注入位移（每拍排空约 1/3，保底 1px），位移总和精确守恒。
- **切回**：触发区 = 主控方向上全部暴露边缘。需先向屏幕内部移动 ≥6px 激活武装，防止进入瞬间反弹；随后在暴露边缘贴边向外推累计 ≥8px 即交还控制权。
- **防抖短冷却**：切换成功或会话正常结束使用 200ms 防抖短冷却，消除 1.5 秒硬性冻结，支持连续平滑往返穿梭；连接或握手失败才锁定 1 秒冷却防日志刷屏。
- 看门狗：主控机 1s ping、副机 pong 应答；副机 5s / 主控 15s 收不到对端消息即释放。
- 入口显示器默认恒为主显示器，可用被控端配置 `kvm_entry_monitor` 显式指定。
- 紧急退出：主控机 `Ctrl+Alt+Shift+X`。

### 8.3 已知限制

- 对 UAC/锁屏等安全桌面无法注入。
- 主控机控制期间本地输入被低级钩子吞掉，Raw Input 提供未裁剪位移。
